## 1. swap 加固三件套（2026-09-13）

### 背景与动因

加固前系统处于最脆弱的组合：

- `swap = 0`，且 `vm.swappiness = 0`（等于没有内存兜底）
- 业务 JVM（systemd 服务 `java-server`）的 `oom_score_adj = 0`、`oom_score = 811`——内存紧张时是 OOM 首要牺牲目标
- 而同机 PostgreSQL 主进程已被保护（`oom_score_adj = -900`），保护关系恰好颠倒
- 系统处于内存超卖承诺状态（`Committed_AS` 约 3.24 GB 超过 `CommitLimit` 约 1.74 GB）

决策过程与只读摸底数据见 Issue #21（摸底全程零影响，有前后基线对照证明）。

### 实施内容

2026-09-13 23:19 完成，**全程未重启任何服务**：

| # | 事项 | 落点 | 说明 |
|---|------|------|------|
| 1 | swapfile 2 GB | `/swapfile`，并写入 `/etc/fstab` 持久化 | 根分区为 ext4，用 `fallocate` 创建 |
| 2 | `vm.swappiness` 0 → 10 | `/etc/sysctl.d/99-apsara-sysctl.conf` | 原值为云环境默认生成的 0，改为温和换出 |
| 3 | JVM OOM 保护 `-500` | `/etc/systemd/system/java-server.service.d/oom.conf`（drop-in） | 重启后仍生效；对运行中进程另行写入 `/proc/<MainPID>/oom_score_adj` 即时生效 |

### 验证结果

- `swapon --show`：`/swapfile` 2 G 已激活；`free` 显示 Swap 2047 MB
- `sysctl vm.swappiness`：10
- JVM `oom_score` 由 811 降至 426，不再是首要牺牲目标
- 零影响证明：`MainPID`、`NRestarts`、`ActiveEnterTimestamp` 三项在实施前后完全一致

### 回滚步骤（完整可逆，逐段可独立执行）

```bash
# 3) 撤销 JVM OOM 保护
MPID=$(systemctl show java-server -p MainPID --value)
echo 0 > "/proc/$MPID/oom_score_adj"
rm -f /etc/systemd/system/java-server.service.d/oom.conf
rmdir /etc/systemd/system/java-server.service.d 2>/dev/null || true
systemctl daemon-reload

# 2) 恢复 swappiness 为 0
sed -i 's/^[[:space:]]*vm\.swappiness[[:space:]]*=.*/vm.swappiness = 0/' /etc/sysctl.d/99-apsara-sysctl.conf
sysctl -w vm.swappiness=0

# 1) 移除 swapfile
swapoff /swapfile
rm -f /swapfile
sed -i '\|^/swapfile none swap sw 0 0$|d' /etc/fstab
```

> 实施当时对 `/etc/fstab` 与 `/etc/sysctl.d/99-apsara-sysctl.conf` 做了备份，位于服务器 `/root/swap-hardening-backup-<时间戳>/`，也可从备份直接恢复。
> 完整的实施/回滚脚本在操作者本机 `.qoder/`（不入库）；以上命令已自足，换机后无需脚本也能执行。
