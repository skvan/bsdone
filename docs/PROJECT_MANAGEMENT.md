# 项目管理流程

> 本项目所有任务、进度和讨论都在 GitHub 上进行。
> 本文面向全体成员（含非技术成员），看完即可上手。

仓库地址：<https://github.com/skvan/bsdone>

---

## 一、一分钟上手

| 你想做什么 | 去哪里 | 怎么做 |
|-----------|--------|--------|
| 发现 Bug / 想提需求 | Issues | 点 **New issue**，选对应模板填写 |
| 看整体进度 | Projects（看板） | 打开项目看板，看卡片分布在哪些列 |
| 跟进某件事 | 对应 Issue 的评论区 | 直接评论，或 @ 相关成员 |
| 了解流程规则 | 本文件 | 继续往下读 |

非技术成员只需要用到 **Issues** 和 **看板**，不需要安装任何工具、不需要写代码。

---

## 二、看板（Projects）

看板共 5 列，卡片在不同列之间移动，代表任务在不同阶段：

| 列 | 含义 | 谁负责移动 |
|----|------|-----------|
| 需求池 | 收集想法，还没排期 | 任何人发现有价值的需求都可以放进来 |
| 待办 | 已确认要做，等待开工 | 成员可把认可的需求从需求池移入；负责人有最终排期权 |
| 进行中 | 正在做 | 开始动手的人拖进此列 |
| 待确认 | 开发做完，等待确认效果 | 开发完成后移入，并在 Issue 里 @ 提需求的人 |
| 已完成 | 确认没问题 | **提需求的人**亲自验收后拖入 |

提示：看板卡片与 Issue 一一对应，点卡片可以跳转到对应的 Issue 看详情。

## 三、Issue：所有任务的起点

### 三种模板怎么选

| 模板 | 适用场景 | 例子 |
|------|---------|------|
| 缺陷报告 | 现在能用的功能坏了、报错、显示不对 | 登录点了没反应 / 比分显示错误 |
| 功能需求 | 想要一个现在还没有的新能力 | 希望增加导出报表功能 |
| 日常任务 | 与产品功能无关的杂事 | 更新球队资料 / 检查配置 / 整理文档 |

模板会自动带上对应的类型标签。尽量都通过模板创建，不要只在微信/口头交代任务——**没有 Issue 的事，等于没有登记，容易被遗忘**。

### 标签怎么选

每个 Issue 挂一个「类型」+ 一个「优先级」。拿不准就空着，负责人会帮忙补。

**类型（这是什么事？）**

| 标签 | 什么时候选 | 例子 | 一句话判断 |
|------|-----------|------|-----------|
| 缺陷 | 本来好用的功能坏了 | 登录没反应、比分显示错误 | 坏了 |
| 功能 | 想要一个现在没有的新能力 | 希望增加导出报表 | 没有，想要 |
| 改进 | 功能有，但用着不顺手 | 页面加载慢、要填的字段太多 | 有，但不好用 |
| 任务 | 跟产品功能无关的杂事 | 更新球队资料、整理文档 | 就是一件事 |

**优先级（这事多急？）**

| 标签 | 什么时候选 | 例子 |
|------|-----------|------|
| P0 紧急 | 线上坏了，所有人都用不了，立刻修 | 网站打不开、无法登录 |
| P1 高 | 严重影响使用，本版本必须解决 | 核心流程报错，但有临时绕路 |
| P2 中 | 有影响但不着急，正常排期 | 某页面偶尔卡顿 |
| P3 低 | 锦上添花，有空再做 | 换个图标颜色 |

## 四、开发流程（开发成员）

所有代码变更都要走下面的流程，**不允许直接推送 main 或 v1.0/dev**：

1. **认领任务**：在 Issue 里回复认领（或由负责人指派），把看板卡片拖到「进行中」
2. **拉分支**：从 `v1.0/dev` 拉出功能分支，命名以 `feature/` 开头
   ```bash
   git checkout v1.0/dev
   git pull
   git checkout -b feature/简短描述
   ```
3. **开发 + 本地验证**：遵循 `AGENTS.md` 中的编码规范
4. **提 PR**：目标分支选 `v1.0/dev`，按模板关联 Issue（在描述里写 `Fixes #编号`）
5. **CI + 审核**：`Backend Compile Check` 通过后，由负责人审核并合并
6. **验收**：开发完成后把卡片拖到「待确认」并 @ 提需求的人；提需求的人确认效果后拖入「已完成」
7. **发布**：负责人把 `v1.0/dev` 合并回 `main` 并打 Tag

### 分支与环境对应关系

| 分支 | 环境 | 说明 |
|------|------|------|
| `main` | 生产环境 | 阿里云线上版本，受保护 |
| `v{版本号}/dev` | 测试环境 | 当前为 `v1.0/dev`，汇总本版本所有功能 |
| `feature/*` | 本地开发 | 每人从对应 dev 分支拉出 |

## 五、自动化规则（不用记，了解即可）

| 什么时候 | 会发生什么 |
|---------|-----------|
| 新建 Issue | 自动出现在看板中 |
| PR 描述写 `Fixes #编号`，PR 被合并 | 对应 Issue 自动关闭，看板卡片自动移入「已完成」 |
| Issue 被关闭 / 重新打开 | 看板卡片状态自动同步 |

## 六、权限说明

| 谁 | 权限 |
|----|------|
| 全体成员（协作者） | 提交 Issue、评论、看板拖卡片、提交 PR |
| 保护分支 `main` / `v*/dev` | 任何成员不能直接推送，必须通过 PR + CI 检查 |
| 负责人（skvan） | 仓库管理员：审核合并 PR、发布版本 |

说明：只有需要写代码的成员才要拉取代码、提交 PR；非技术成员用 Issues 和看板就能完成全部协作。

## 七、常见问题

**Q：标签拿不准选哪个？**
空着就行，负责人审核时会补上。

**Q：Issue 标题怎么写？**
写清楚「在哪、发生了什么 / 想要什么」即可，不用套固定格式。

**Q：有想法但还没想清楚？**
先放进「需求池」，不用写得很完整，之后再细化。

**Q：任务做完了但没人确认？**
在 Issue 里 @ 提需求的人，并把卡片拖到「待确认」。

**Q：怎么知道某个功能做到哪了？**
打开看板找对应卡片（可按标签筛选），或搜索 Issue 标题。

**Q：紧急问题怎么走？**
先提缺陷报告并说明影响范围（所有人无法使用），再直接 @ 负责人，不要等。
