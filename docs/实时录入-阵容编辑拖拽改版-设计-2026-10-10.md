## 三、状态模型（复用现有结构，不发明新形状）

```
rows[]     // 下标 = 棒次；元素 = 现有行对象 {id,name,number,teamId,position,stats}；空位 = id<0 占位行
           // 【长度固定】无 DH 时 9 行、含 DH 时 10 行（DH 恒为最后一行）；空行（id<0）恒排在尾部
           //  → 「棒次收拢」= 移出后把空行归位到尾部，而非删除行；payload 形状与旧件完全一致
bench[]    // 替补区（旧 T/k）
pool[]     // 派生：名册 − rows − bench（旧 Be/Ve）
fieldingPitcherId  // 仅守备投手（旧 G/q）
lastDhAddedFromPoolId // 旧 A/D
```

**投手与打线的映射**（沿用旧件联动语义，UI 表达更清晰）：投手丘卡槽的内容 = `rows` 中的 P 行（投手打击）**或** `fieldingPitcherId`（投手仅守备）；两者互斥表达，切换规则见 §五。

四个动作（`useLineupBoard` 唯一的状态出口）：

```
placeAtSlot(player, posCode):
  // 分支一：player 已在 rows 中（含从球场卡槽拖来）
  //   目标槽为空 → 仅改该行 position = posCode，棒次不变（决策 #4）
  //   目标槽有人 → 该行与目标行【整体对调】（球员+位置一起换，棒次随之互换）（决策 #5）
  // 分支二：player 来自池/替补（不在 rows）
  //   目标槽为空   → 填入尾部第一个空行 {…player, position:posCode}（＝首次落位定棒次）
  //   目标槽有人   → 目标行改写为 {…player, position:posCode}；原占用者转出到
  //                  拖动起点所在区域（起点是池→回池；起点是替补→回替补）
  //   无空行且目标槽有人 → 允许（等价整行顶替 + 原占用者转出）
  //   无空行且目标槽为空 → 理论不可达（9 行满员时不可能存在空槽）

sendBackToBench(rowIndex):
  该行还原为占位行并把空行归位到尾部（棒次连续）；球员并入 bench（去重）；
  若该球员 === lastDhAddedFromPoolId → 清该标记

reorderBatting(oldIndex, newIndex):
  仅对 rows 前 k 个非空行做 splice 重排（沿用旧 Oe 写法），空行恒留尾部

applyTemplate(slots, benchPlayerIds, pitcherId):
  按 slots 顺序重建 rows（映射沿用旧 sl()），bench 覆盖，pitcher 同步，
  lastDhAddedFromPoolId 清空
```

派生与门控（**全部沿用旧实现语义**，仅搬进 composable）：

- `slotOf(code)` = rows 中 `position` 匹配行
- 校验：`validateRosterPositions(rows.map(position), gameMode)`，含 `ke()` 特例（长度=C 且位置全空时 msg 置空）
- 守备投手提示：旧 `se/ie` = `rows.length===C && ok && 无 P`（此时该投手不打击，须指定后才可开始录入）
- 开始录入门控：旧 `Pe`；保存门控：旧 `Te`

## 四、交互规格（细则）

### 4.1 四个区域

1. **球场**（内野俯视图）：10 卡槽（9 守备位 + DH）；投手丘只有一个卡槽（守备投手），卡片带「仅守备」徽标表示不打击
2. **打线列表**：第 N 棒 ↔ 球员 ↔ 位置（sortablejs 内部排序）；**同时是拖放落点**（独立拖人进入）
3. **替补区**：bench 卡片 + 「批量添加」按钮
4. **可用球员池**：pool 卡片（名册 − 阵容 − 替补）

### 4.2 拖放路径与结果

| 起点 → 终点 | 结果 |
|---|---|
| 池/替补 → 空卡槽 | 落位；该球员获棒次（填尾部第一个空行） |
| 池/替补 → 已占用卡槽 | 两人互换（位置+棒次）；被换下者转出到**起点所在区域**（池或替补） |
| 池/替补 → 打线列表 | **独立追加打击者**：位置码取该人的守备位；不在守备阵容则记 `DH`；打线满员（棒球 10 人上限）时拒绝并提示 |
| 卡槽 → 打线列表 | 已在打线中的人 → 仅改棒次（按落点位置插入） |
| 卡槽 → 空卡槽 | 移动守备位置，棒次不变 |
| 卡槽 → 已占用卡槽 | 两人互换（位置+棒次） |
| 池/替补/卡槽 → 替补区 | 移出：该行还原占位并把空行归位尾部（棒次连续，payload 行数不变）；该球员进替补区 |
| 池 → 池 / 替补 → 替补 | 无操作（不改状态） |
| 替补 → 池 | 从替补名单移除（等价旧多选取消勾选） |
| 任意 → 非落点区域 | 无副作用，卡片归位 |

### 4.3 点选点放（触屏兜底）

点卡片 → 进入「待放置」态（卡片描边高亮 + 合法卡槽呼吸高亮、非法卡槽置灰）→ 点目标卡槽 = 执行与拖拽相同的 `placeAtSlot` → 再点原卡片或空白处取消。

### 4.4 卡片操作面板（点击已落位卡片/池卡片触发，小屏用 bottom-sheet）

- 已落位卡片：① 更换球员（带搜索下拉，复用旧 `lineup-player-select` 逻辑）② 移到其他位置（列空闲位）③ 移出（回替补区）
- 池/替补卡片：① 放入位置（列空闲位）② 加入替补/移出替补

### 4.5 触屏参数

- 卡片 `touch-action: none`；长按 180ms 进入拖起态（`delay` 语义自实现，防与页面滚动冲突）
- 拖起后卡片跟手（`pointermove` 直接改 transform），落点判定用 `dropzone({overlap: 0.5, checker})`，命中容差由 `overlap` 值调节
- 松手未命中落点：回弹动画 150ms

### 4.6 响应式（≤768px，沿用 `useMediaQuery("(max-width: 768px)")`）

球场与打线列表上下堆叠；球场宽度撑满；卡片字号上调一档；操作面板改 bottom-sheet。

## 五、投手 / DH 规则（单卡槽模型，写死，勿凭直觉改）

**球场只有 9 个守备卡槽**（含投手丘一个）；**投手「是否打击」唯一表达处是打线列表**；DH 卡槽表示「指定打击」这一打击位。

| 合法态 | 投手丘 | DH 卡槽 | 打线列表 | 校验来源 |
|---|---|---|---|---|
| 9 人 · 投手制 | 有守备投手 | 空 | 8 守位 + 投手（9 棒） | `X(c)`：P×1 + 8 守位，size=9 |
| 9 人 · DH 制 | 有守备投手（**仅守备**徽标） | 有人 | 8 守位 + DH（9 棒） | `h(c)`：DH×1 + 8 守位，size=9 |
| 10 人 | 有守备投手 | 有人 | 8 守位 + DH + 投手（10 棒） | `C(c)`：P×1 + DH×1 + 8 守位，size=10 |

交互规则：
1. **拖人上投手丘**：打线**无 DH** → 该人同时进打线（填尾部空行，position=`P`）；打线**已有 DH** → 仅记为守备投手、**不进打线**，卡片显示「仅守备」徽标（决策 15）
2. **拖人进 DH 卡槽**：若投手当前在打线 → **自动把投手移出打线**并提示「已按 DH 制把投手移出打线；如需 10 人打击，请把投手拖回打线」
3. **需要 10 人打击** → 把投手（或任一守备员）**拖进打线列表**即可（决策 14）
4. **移出 DH**：若投手处于「仅守备」→ **投手自动回到打线**（填尾部空行，position=`P`），恢复 9 棒（决策 16）
5. 「仅守备投手」不占棒次、不进 `rows`，只写 `fieldingPitcherId`；打线 9 棒且无 P 时才要求必填（沿用旧 `se/ie` 语义）
6. **打线列表独立拖人**：位置码取「该人的守备位；不在守备阵容则 `DH`」；棒球打线满 10 人（现有上限）时拒绝并提示；`EP` 与 10-12 人打击见 Issue #274

## 十一、验收清单（测试人员照做）

前置：管理后台 → 赛程 → 某场 scheduled 比赛 → 「编辑」进入「确认先发阵容」。

1. 拖到空位 → 卡片落位、打线列表出现该球员并占棒次，先拖者棒次靠前
2. 拖到已占用位 → 两人互换（位置 + 棒次），无重复球员
3. 打线排序 → 顺序变化，场上守备位不变
4. 拖回替补 → 卡槽变空、球员进替补、棒次连续无洞
5. **DH 与投手联动** → DH 卡槽放人：投手自动移出打线、投手丘卡片出现「仅守备」徽标与提示；把投手拖回打线列表 → 变 10 人打击且校验通过；移出 DH → 投手自动回打线（9 棒）；打线无 P 时出现「须指定先发投手」红字
5b. **打线列表独立拖人** → 从池直接把球员拖进打线列表 → 追加为打击者（不占守备位）；打线满 10 人时拒绝并提示
6. 点选点放（手机）→ 点卡片高亮合法位、点卡槽完成落位、再点原卡片取消
7. 模板应用 → 二次确认 → 卡片按模板落位
8. 保存后刷新（URL 带比赛 ID）→ 阵容原样恢复
9. 开始录入 → 跳转录入页，阵容一致

回归点：三按钮 disabled 与跳转 / 校验文案与错误高亮 / 仅守备投手不占打序 / **垒球比赛仍显旧表格可用** / 无模板权限者看不到模板按钮。

## 十二、风险与缓解

| 风险 | 缓解 |
|---|---|
| interactjs 首次在本项目使用，触屏手感未实证 | 编码第一步做最小 demo 验证四条路径（池→空槽、池→占槽互换、槽→槽、点选点放）后再铺开 |
| 双引擎手势冲突（interactjs 与 sortablejs） | 两者作用于互不重叠的 DOM 区域（球场区 vs 打线列表）；验收单列一条"同时操作无异常" |
| 页面上卡片同时出现在卡槽与打线列表 | 两处均为 Vue 渲染的独立节点，非同一 DOM；拖放引擎不搬 DOM，不存在节点争抢 |
| 大范围重写引入回归 | 旧件不删（垒球兜底 + 对照）；回归点逐条验收；保存/快照链路零改动 |
| 本批校验上限沿用现状（棒球 ≤10 人） | 「更多人打击」用户在批次 2（#274）前会碰到 10 人上限提示；提示文案写明上限与去向，避免误判为缺陷 |
| 批次 2 依赖本批规则层 | `placeAtSlot` 与打线列表落点先按「任意长度」实现（仅由校验挡住），避免批次 2 返工 |
