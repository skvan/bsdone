# 实时录入·换人后续：逐位置守备局数 / 箱线图换人事件 / 撤销回滚统计（设计）

- 关联：#478 第 2、3、4 项；前置 #477 换人事务、#489 半局自动保存
- 基线：`v2.3/dev @ 0d6c971`（2026-10-28）
- 性质：设计稿，不含实现；灰度与拆分建议见文末「落地顺序」

## 总原则

1. **事实单一来源**：阵容/统计以 `bs_game_player_stat` + 现场快照为准，换人以 `bs_game_substitution_event` 为准；展示层不得再用 `listOrder` 猜换人。
2. **引擎字段只读**：`pitchR/er/unearnedR/pendingR` 由自责分引擎独占写入，撤销不得用 payload 覆盖。
3. **历史不造假**：没有逐位置数据的存量场次不做推断回填，展示回退到现有总口径并明确标注。
4. **最小改动面**：`GameDetailContent.js` / `GameDetail.js` / `LiveGameWatch.js` 均为「行为保真移植」文件（文件头注明勿手改），优先在父页面/独立组件落地，必要时才做定点小改。

## 一、第 2 项：逐位置守备局数

### 现状（证据）

- `bs_game_player_stat.def_inn`（`Double`）是**球员级总守备局数**：`GamePlayerStat.java:247-249`。
- 实时录入每出局给「投手 + 场上野手」累加 `fielding.ip`（棒球局数记法），不区分位置：`LiveGame.js:8300-8306`（`Ipy`）。
- 保存时把 `fielding.ip` 直接当 `defInn` 发出：`LiveGame.js:10910`（`Eo` → `defInn:p.ip??0`）。
- 后端只透传，不计算：`GameService.java:1135-1137`（saveLive）、`879`（saveResult）。
- 箱线图守备表按球员一行展示 `defInn`：`GameDetailFieldingTable.vue:46,58-60`。
- 换位/代守后同一球员的局数全部落在总数里，无法拆分——即本项缺口。

### 目标

- 记录 **球员 × 守位** 的守备局数（建议内部用「出局数 outs」整数累计，展示时转棒球记法）。
- 箱线图守备表可按位置拆分展示；`def_inn` 总数保留（向后兼容，由逐位置汇总得到）。
- 覆盖换位、代守、换投、DH、延长局；换到新位置从 0 起算，旧位置保留。

### 方案对比

| 方案 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| **A 新表（推荐）** | 新增 `bs_game_fielding_inn`，唯一键 `(game_id, team_id, player_id, position)`，存 `outs` | 可查询、可聚合、约束清晰；`def_inn` 可由汇总得出 | 新增表/实体/接口/前端装配 |
| B JSON 列 | 在统计行加 `def_inn_by_pos` JSON | 改动最小 | 无法索引聚合；并发整列覆盖；口径易漂移 |
| C 事件推导 | 用换人事件 + 局数反推 | 不新增数据 | 事件不含「每半局在场」信息，DH/换位无法还原，不可靠 |

### 推荐设计（A）

**数据模型（Flyway 新迁移）**

```sql
create table bs_game_fielding_inn (
  id bigserial primary key,
  tenant_id bigint not null,
  game_id bigint not null,
  team_id bigint not null,
  player_id bigint not null,
  position varchar(8) not null,      -- P/C/1B/.../DH 不计入
  outs integer not null default 0,  -- 该位置累计出局数，3 outs = 1.0 局
  is_starter boolean not null default false, -- 该位置是否先发（对应 fielding_gs 语义）
  created_at timestamp, updated_at timestamp,
  unique (game_id, team_id, player_id, position)
);
create index idx_game_fielding_inn_game on bs_game_fielding_inn(game_id);
```

- `def_inn` 总数：新场次保存时由 `sum(outs)` 换算（`outs/3` 取一位小数，如 10 outs → `3.1`），仍写回 `bs_game_player_stat.def_inn`，保证旧查询/旧前端不受影响。
- `position` 变更（守位互换/代守）不改旧行，新增一行；`is_starter` 只由开赛先发标记。

**累计口径（前端）**

- 新增纯函数模块 `liveGameFieldingByPos.js`：`addOut(state, playerId, position)`、`merge`、`toPayload`、`outsToInnings`。
- 球员 `stats.fielding` 增加 `byPos: { "SS": 5, "2B": 3 }`（outs）。
- `Ipy()`（每出局）在累加总 `fielding.ip` 的同时，对每名在场守备员按其**当前守位**累加 `byPos[pos]`；DH 不计守备；投手按 `P` 计。
- 换位/换人无需特殊处理：计数器以位置为键，新位置自然从 0 起。
- 撤销/恢复：随统计快照一起进/出（见第 4 项），保证与 `fielding.ip` 同步回退。
- 保存 payload：`save-live` 新增可选顶层数组

```json
"fieldingInnings": [
  { "teamId": 1, "playerId": 108, "position": "CF", "outs": 18, "isStarter": true },
  { "teamId": 1, "playerId": 111, "position": "CF", "outs": 3 }
]
```

- 语义：**出现该键即视为该场两队全量替换**（先删后插，同一事务）；缺省不触碰，兼容旧客户端。球队范围取 payload 中出现的 teamId（必须属于本场）。
- 读取：`GET /game/{id}/fielding-innings` 返回 `list/total`，按 `team_id, player_id, position` 排序；沿用比赛读取权限与租户隔离。
- 结果页 `save-result` 本期不接（纸质录入无逐位置信息）。

**展示**

- `GameDetailFieldingTable.vue` 增加可选 `fieldingInnings` prop：
  - 有逐位置数据：按 `player × position` 展开多行（POS 列即该行位置），`defInn` 显示该位置局数；同一球员多行相邻。
  - 无数据（存量场次/旧接口失败）：维持现状单行显示 `def_inn` 总数。
- `GameDetail.js` 与 `LiveGameWatch.js` 并行请求 `fielding-innings`，失败不影响主表（该列回退总数）。
- 字段设置（`fieldingFields`）不变；本期不加「合计行」。

**迁移与存量**

- Flyway 建表；上线后新产生/新保存的场次逐步有数据。
- 存量场次不回填（避免把「总局数」伪装成某位置局数）；箱线图回退总数，不出现空列。

**测试**

- 前端单测：`liveGameFieldingByPos`（累加、换位、换人、DH、延长局、outs→局数格式、payload 序列化）。
- 后端单测：替换语义（缺键不动、带键先删后插、跨队/越权拒绝、引擎行不受影响）；读取排序与权限。
- E2E：先发 SS 打 1 局 → 与 2B 互换 → 再打 1 局 → 保存；箱线图出现 `SS 1` 与 `2B 1` 两行，球员总数仍为 2。

## 二、第 3 项：箱线图直接消费换人事件

### 现状（证据）

- 事件表与接口已完整：`GameSubstitutionEvent`（sequence/changeSeq/transactionId/slot/inning/topBottom/outPlayerId/inPlayerId/outPosition/inPosition）、`GET /game/{gameId}/substitutions`（`GameService.java:426-431`，按 sequence 升序）。
- 前端 API 已具备 `gameApi.substitutions(id)`（`business.js:261`），但**无任何页面调用**。
- 箱线图（`GameDetailContent.js`，由 `GameDetail.js:14` 与 `LiveGameWatch.js:1076-1078` 渲染）只吃 `stats`：
  - 打击行排序 `listOrder → battingOrder → playerId`（`:1050-1057`）；
  - 投手行排序 `listOrder → pitcherOrder`（`:1111-1112`）；
  - 替补行 = `battingOrder` 为空的行，与换人事件无关联。
- 文件头注明「行为保真移植…勿手改」。

### 目标

- 在箱线图区域展示**换人顺序 / 槽位 / 局次（上下场时间）/ 上下场球员与守位**，数据直接来自事件表。
- 不再依赖 `listOrder` 推断「谁换了谁」；事件缺失（存量场次）时保持现有展示，不报错。

### 方案对比

| 方案 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| **A 独立「换人记录」区块（推荐）** | 新组件 `GameDetailSubstitutionTable.vue`，父页面取数并渲染在箱线图下方 | 零改动移植文件；可独立测试；信息完整 | 与打击行不联动（不改变行序） |
| B 打击表内徽标/重排 | 在 `GameDetailContent` 内用事件给替补行加「3局上 换下 #8」并重排 | 视觉最贴合「箱线图」 | 需改移植文件；排序/分组回归风险高 |
| C 后端读模型 | 后端聚合成「换人时间线」返回 | 前端最薄 | 多一层接口与缓存，当前数据量不需要 |

### 推荐设计（A，分两阶段）

**阶段 1（本项主体，低风险）**

- 新组件 `components/admin/GameDetailSubstitutionTable.vue`：
  - props：`substitutions`、`teams`、`playersMap`、`gameMode`。
  - 按 `transactionId` 分组（同事务多行），组头显示「第 N 次换人 · 3局上」；组内按 `changeSeq` 列每笔变化：
    - `SUBSTITUTION`：第 8 棒 CF `#8 张三` → `#11 李四`（CF）
    - `POSITION_CHANGE`：`#6 王五` SS → 2B
    - `PITCHING_CHANGE`：投手 `#18 赵六` → `#21 钱七`
    - `DH_CANCEL`：取消 DH，`#1 投手` 进入第 5 棒
  - 只读，无交互；空数组/请求失败时整个区块不渲染。
- 父页面取数：
  - `GameDetail.js`、`LiveGameWatch.js` 在加载 stats/snapshot 时并行 `gameApi.substitutions(gameId)`；
  - `playersMap`/`teams` 两页均已有，直接复用；
  - 请求失败仅 `console.warn`，不影响箱线图主表。
- 时间口径：**以 `inning + topBottom` 为「比赛时间」**主展示；`BaseEntity.createdAt` 可作悬浮补充（HH:mm），不新增字段。
- 事件过滤：为第 4 项的 `voided` 预留——阶段 1 返回不含 `voided` 字段时按未作废处理。

**阶段 2（可选，视验收反馈）**

- 用事件给替补行加行内徽标（「换人 · 3局上」），并仅对能匹配 `inPlayerId` 的行改用 `(slot, sequence)` 排序，其余仍回退 `listOrder`；
- 必须单列回归：先发/替补/二刀流/10–12 棒/取消 DH 五类场次的打击表顺序与现状一致。

**测试**

- 单测：分组/文案格式化纯函数（事务分组、顺序、DH_CANCEL 文案、缺失球员回退 `#id`）。
- E2E（本地 mock `/game/10/substitutions`）：比赛详情与观赛页各渲染一次换人记录；无事件时区块隐藏；请求 500 时主表不受影响。
- 后端本期无改动（若加 `includeVoided` 参数随第 4 项落地）。

## 三、第 4 项：撤销回滚球员统计（含换人事件）

### 现状（证据）

- 撤销栈 `$e` 的快照内容：游戏状态 `Wl()`、比分 `Xl()`、阵容 `Yl()`（深拷贝 lineup/bench，**球员对象自带 `.stats`**）、打席摘要、playEvents、runLedger、日志；**不含权威统计集合 `playerStatsById`**（`LiveGame.js:7815-7838`）。
- 恢复 `ns()` 只恢复上述字段与阵容对象，不恢复 `playerStatsById`（`7856-7874`）；`playerStatsById` 是观赛同步与快照导出的来源（`5506-5526`、`7726-7773`），撤销后会保持旧值。
- 撤销/重做**不触发保存**（`7984-8041`）；手动/自动保存把当前球员对象统计 upsert 到后端（`11000-11040`）。
- 后端 `save-live` 只 upsert、不删除 payload 之外的行（`GameService.java:258-329`）；`save-result` 才删除未命中行（`757-762`）。→ 被撤销的「新球员统计行」会残留。
- 换人事件**只追加**，无删除/作废接口（`332-359`）；换人提交后撤销只回退前端阵容快照（`10087`），事件仍在。
- 自责分：每个打席后按半局调用重建接口（`7338-7351`）；撤销恢复 `playEvents` 但**不重算**，引擎字段（R/ER/UER/PENDING）保持撤销前状态。

### 目标

- 撤销/重做后：前端统计、后端统计、换人事件三者与目标检查点一致。
- 引擎字段保持「引擎单一写方」：撤销后由引擎按恢复后的 playEvents 重算，而不是前端覆盖。
- 不破坏 partial payload 兼容：普通保存仍是 upsert，只有显式「全量状态保存」才替换。

### 方案对比

| 方案 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| **A 全量快照 + 全量保存 + 事件作废（推荐）** | 历史项纳入统计与逐位置局数；撤销后静默全量保存；事件按水位软作废；受影响半局重算 ER | 与现有快照架构同构；后端语义明确；可审计 | 需扩快照体积、加两个接口语义 |
| B 事件冲销（delta journal） | 每个动作记录统计增减，撤销反向冲销 | 快 | 与现有快照体系重复；ER/换人/漏记纠错易漂移 |
| C 统计版本表 | 每次保存落版本，撤销选旧版本 | 审计最强 | 存储/接口/清理复杂，超出本期 |

### 推荐设计（A，分两期）

**P1：统计全量回滚（先解决数据正确性）**

1. 前端历史项新增：
   - `playerStats`：规范化统计映射（与观赛快照 `playerStatsById` 同构）；
   - `fieldingByPos`（第 2 项落地后加入）；
   - `substitutionWatermark`（见 P2）。
   - 快照体积评估：≤ 30 名球员 × 小型对象，栈上限 `Fs` 不变，可接受。
2. 撤销/重做：
   - 恢复时把 `playerStats` 写回球员对象与权威集合（复用 `applyRestoredData` 的合并逻辑）；
   - 末尾调用 `hs({ silent:true, fullState:true })` 走 #489 的串行保存链，避免旧 payload 后写覆盖；
   - 保存失败：保留撤销后的前端状态，错误提示「统计尚未同步」，下次保存继续全量。
3. 后端 `save-live` 新增 `fullState:true`（或 `statsMode:"replace"`）：
   - 仅当该键为 true：对 payload 中出现的每个 `teamId`，删除该队在本场中**未被 payload 命中**的统计行，再 upsert；
   - 引擎托管的投手行（`is_engine_managed` 场景）保持现有保护，不物理删除；
   - 缺省 false 时行为与现在完全一致（旧客户端/结果页不受影响）。
4. 测试：
   - 后端：replace 只删本场本队未命中行；不删引擎行；缺省不删；越权/跨场拒绝。
   - 前端单测：快照包含统计，恢复函数回填。
   - E2E：打一球 → 自动保存 → 撤销 → 断言第二次 save-live 为全量且统计回退；被撤销球员行不再出现在箱线图。

**P2：换人事件作废 + ER 重算（数据一致性收口）**

1. 事件表加 `voided boolean default false`、`voided_at timestamp`（保留审计，不物理删）。
2. 新接口 `POST /game/{id}/substitutions/void-after`，body `{ "sequence": 12 }`：
   - 将本场 `sequence > 12` 的未作废事件标记作废；返回作废条数；
   - 幂等；沿用比赛写入权限与租户隔离；
   - `listSubstitutions` 默认只返回未作废（审计可加 `?includeVoided=true`）。
3. `save-live` 响应返回 `lastSubstitutionSequence` = 本场当前**未作废**事件的最大 `sequence`（无事件为 0）。前端每个历史项记录该水位；撤销到某检查点时调用 `void-after(watermark)`。
   - 换人提交成功（`finishSubstitutionMode`）后同样记录新水位，保证「撤销整体撤回本次换人」时事件一起作废。
4. ER 重算：
   - 撤销前后对比 `playEvents`，得到受影响的 `(inning, half)` 集合；
   - 复用现有 `reconstructEarnedRuns` 逐半局重算（失败则提示「自责分待重算」，不回滚撤销本身）；
   - 重算完成后再执行全量保存，保证引擎字段以服务端结果为准。
5. 测试：
   - 后端：void-after 幂等、只作废尾部、列表默认过滤、审计参数、权限；
   - E2E：提交换人 → 撤销 → 事件作废 + 箱线图换人记录消失 + 阵容/统计回到提交前；
   - ER 用例：撤销含得分的半局 → 责任投手 R/ER 与撤销后 playEvents 一致。

### 风险与约束

- **ER 引擎时序**：重算与全量保存必须串行（现有 `earnedRunSyncPending` + `hs` 串行链可复用），否则可能保存旧 ER。
- **事件水位**：若未来支持多端并发录入，水位作废需加乐观校验（请求水位必须等于当前最大未作废 sequence），本期先按单端设计。
- **快照膨胀**：历史栈上限不变；若实测明显变大，再考虑只存 diff。
- **审计**：作废事件保留原始行，箱线图/接口默认过滤；后台审计视图后续再加。

## 落地顺序（建议）

1. **4-P1 统计全量回滚**：先解决「撤销后统计/幽灵行不回退」的数据正确性问题，也为第 2 项的逐位置快照打好扩展点。
2. **第 3 项 阶段 1 换人记录区块**：独立、低风险，立即让事件表产生产品价值。
3. **第 2 项 逐位置守备局数**：数据模型 + 累计 + 展示；快照与全量保存字段随之扩展。
4. **4-P2 事件作废 + ER 重算**：依赖第 3 项的展示过滤与第 2 项的统计扩展，最后收口一致性。

每项单独 PR；第 2 项先更新「数据模型设计/统计实体」与 API 参考，第 4 项先补 API 参考的 save-live / substitutions 语义。

## 验收口径（汇总）

- 第 2 项：同一球员在两个守位各守 1 局，箱线图显示两行各 1 局，球员总数 2；换人后的新球员从 0 起算；存量场次不出现空列。
- 第 3 项：有事件的场次展示换人顺序/槽位/局次/上下场球员；无事件或接口失败时箱线图与现状一致。
- 第 4 项：撤销/重做后前端与后端统计一致、无幽灵行；撤销已提交换人后事件作废且箱线图不再展示；引擎字段与撤销后 playEvents 重算结果一致。
