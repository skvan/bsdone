## 简介
本文件聚焦于棒球统计实体的数据模型与计算逻辑，覆盖比赛球员统计数据（GamePlayerStat）、击球热区（HitSpray）、精彩时刻（HighlightMoment）、历史记录（HistoryRecord）等关键实体。文档重点说明：
- 字段定义与业务含义（含击球率、本垒打数、防守数据等专业指标）
- 统计数据的聚合计算与展示格式
- 缓存策略与性能优化建议
- 历史数据归档、报表生成与导出支持
- 统计查询的SQL优化与索引设计建议

## 项目结构
围绕统计能力的相关代码主要分布在以下层次：
- API层：暴露统计相关接口（如击球热区、精彩时刻、历史记录）
- Service层：负责统计聚合、格式化、分页与排序
- DTO层：承载对外展示的统计结果（击球/投球/防守三维度）
- Repository/Mapper层：提供数据访问与复杂查询（由服务调用）

## 核心组件
- 比赛球员统计数据（GamePlayerStat）
  - 用于记录单场比赛中每位球员的击球、跑垒、防守、投球等多维原始统计
  - 服务层提供按比赛查询、去重与“丰富度”择优策略，保证同一角色在同一比赛中保留信息更完整的记录
- 击球热区（HitSpray）
  - 通过API提供保存、批量保存与按比赛/球员/队伍查询的能力，支撑可视化与战术分析
- 精彩时刻（HighlightMoment）
  - 提供列表、创建、更新、删除等基础CRUD能力，支持按主题类型、媒体类型、状态等筛选
- 历史记录（HistoryRecord）
  - 提供分页列表与创建能力，支持按目标类型、关联对象、记录类型、时间范围等条件检索，便于审计与回溯

## 详细组件分析

### 比赛球员统计数据（GamePlayerStat）
- 职责
  - 存储每场比赛的球员原始统计（击球、跑垒、防守、投球）
  - 提供按比赛查询与去重策略，确保同一角色在同一比赛中仅保留信息最完整的一条
- 关键字段（示例）
  - 击球/跑垒：PA、AB、R、H、RBI、HR、InsideParkHR、SB、SO、Doubles、Triples、BB、IBB、HBP、IO、CS、SH、SF、E、GDP
  - 投球：IP、ER、PitchH、PitchDoubles、PitchTriples、PitchSh、PitchSf、PitchBbHp、PitchSo、PitchHr、PitchInsideParkHr、PitchIo、Np、Wp、Bk、PitchPa、PitchBf、PitchAb、PitchR、Go、Fo
  - 防守：PO、A、TC、DP、INN、PB、CatcherSb、CatcherCs
  - 角色标识：IsPitcher、BattingOrder、PitcherOrder、ListOrder、Position、FirstPosition
  - FirstPosition（V20261028160000 新增）：本场首次上场防守时的守位，用于盒子比分守备表归组；
    之后场上换位不更新。DH/PH/EP 不守备，该列为空；旧数据为空时前端回退 Position 并按守备证据过滤代打/代跑。
  - 守备汇总口径：仅取 Position 非空且非 DH/PH/EP 的行；以 `IsPitcher=0` 的球员行为主（GP 按场去重），
    `Position=P` 照常计入（野手改投后整行守备数据不丢失）；投手并行行（`IsPitcher=1`）仅在该球员本场
    没有带守备数据（TC/PO/A/E/DP/PB/CS/SB/INN/GS）的可计入球员行时补计，补计需上述任一项有值，避免二刀流重复累计。
    显式按 P 筛选时零动作投手行也补入，但同位置已有带数据球员行时不重复；新增复合索引 `(game_id, player_id, team_id, is_pitcher)` 支撑该去重查找。
  - 捕手专项：PB/CS/SB 按行无条件累计（捕手后改投不会丢失）；按 C 筛选时同时纳入 `FirstPosition='C'` 或 PB/CS/SB 有值的球员。
- 去重与丰富度评分
  - 构建唯一键：基于比赛ID、队伍ID、球员ID、是否投手、击球顺序、投球顺序、名单顺序、位置
  - 丰富度评分：对关键统计字段非空计数，选择更“丰富”的记录作为最终值
- 典型流程

### 换人事务事件（GameSubstitutionEvent）

- 表名：`bs_game_substitution_event`
- 职责：记录实时录入“换人模式”一次提交的**净变化**，作为箱线图换人顺序、审计与现场重建的显式依据；统计事实仍写 `bs_game_player_stat`
- 关键字段
  - 事务：`transaction_id`（同一次提交共用）、`sequence`（全场顺序）、`change_seq`（事务内顺序）
  - 比赛/球队：`game_id`、`team_id`、`tenant_id`、`inning`、`top_bottom`
  - 变化：`change_type`（`SUBSTITUTION/POSITION_CHANGE/PITCHING_CHANGE/DH_CANCEL`）、`slot`、`out_player_id`、`in_player_id`、`out_position`、`in_position`
- 约束
  - `(game_id, transaction_id, change_seq)` 唯一（`deleted_at IS NULL`），同一事务重试幂等
  - `(game_id, team_id, sequence)` 普通索引，用于按场次/球队回放
- 口径
  - 一次换人模式只记录 before/after 的净变化；同槽中间犹豫/纠错不落事件
  - 棒次仍按 #469 口径：被换下者保留原棒次，换上来的人不带棒次排在其下
  - 被换下者最后守位由统计行 `position`（`lastPosition` 回填）与事件 `out_position` 共同保留
  - 取消 DH 使用 `DH_CANCEL`，换上投手进入原 DH 槽位并占打击行

### 击球热区（HitSpray）
- 职责

- 能力

- 使用场景

### 自责分重建引擎（Issue #149，第一阶段）

`stats/earnedrun` 提供与数据库和 Web 框架无关的半局重放核心，并由服务层负责持久化重建结果；实时记分每次打席后调用重建接口，赛后 `save-live` / `save-result` 不再用客户端值覆盖引擎累计。

**单一写方（#149/#204）**：`pitchR`、`er`、`unearnedR`、`pendingR` 只由 ER 引擎写入。`save-live` / `save-result` 在比赛已有 `bs_earned_run_play`（按 gameId 全局判断，避免换赛事/租户绕过）时忽略 payload 里的 `er`/`pitchR`；直接统计 CRUD（`create/update/delete`）对引擎场次同样生效：create 归零四字段、update 保留四字段并拒绝改比赛/球员/投手身份、delete 拒绝删除投手行。没有引擎数据的 legacy 场次和导入链路仍允许手工写入，便于历史数据修正。重建响应同时返回半局增量 `pitcherTotals` 与库内绝对值 `pitcherAbsoluteTotals`，前端用绝对值回显，刷新后不会重复累加。

- `EarnedRunPlay`：按严格递增顺序输入逐球事件，并分别记录实际出局数增量与无失误重建出局数增量。
- `ScoringRunner`：记录得分跑者、责任投手、上垒来源、若无捕逸等失误是否仍会得分的判断及可审计的人工覆核结果。
- `EarnedRunDecision`：输出 `EARNED`、`UNEARNED` 或 `PENDING`，非自责分同时保留原因。
- `EarnedRunReconstructionResult`：返回实际/重建出局数、逐分判定及按责任投手汇总的 R、ER、UER、PENDING。

核心不变量：

- 棒球与垒球共用同一套 ER/UER 判定规则，不按 `gameMode` 分流。
- 每一分只归属一个责任投手，换投不会改变已在垒跑者的责任投手。
- 失误上垒跑者得分为非自责分，但不能把失误后的所有得分一律判为非自责分。
- 无失误重建局面达到理论第三出局后，因该局延续产生的得分为非自责分。
- 突破僵局预置跑者按非自责分处理。
- 暴投属于投手责任，不因暴投本身自动判为非自责分；仍按失误是否延长半局判定。
- 捕逸跑者若无捕逸仍会得分则按正常局面判断 ER/UER；若不会得分则为 UER；缺少判断时记 `PENDING`，不可将捕逸一律视为 UER。
- 判决仍可能修改时保留 `PENDING`，不得提前计入 ER 或 UER。
- 人工改判必须同时提供原因；最终持久化阶段还需记录操作者和时间。

持久化模型：

- `bs_earned_run_play` 按比赛、局数、上下半局和事件顺序保存实际/重建出局数增量；同一来源事件不可重复写入。
- `bs_earned_run_decision` 每行代表一个得分跑者，保存责任投手、跑者来源、无失误时是否仍会得分、判定状态、非自责原因及人工覆核信息；跑者来源取值与 `RunnerOrigin` 枚举一致（NORMAL、ERROR、TIE_BREAK、WILD_PITCH、PASSED_BALL、INTERFERENCE）。
- `EarnedRunReconstructionService.replaceHalfInning` 在单一事务中删除指定半局旧结果、重放全部事件并写入新判定，避免局部修改造成累计漂移。
- 每次半局全量重建会先读取该半局旧判定，再以新旧 R/ER 差额更新责任投手的 `GamePlayerStat.pitchR`/`er`，重复重建或赛后改判不会重复累计。
- 重建响应除半局增量 `pitcherTotals` 外，还返回全投手库内绝对值 `pitcherAbsoluteTotals`；前端只覆盖绝对值，不累加，刷新/重开比赛后仍幂等。
- `PENDING` 计入投手失分 `pitchR`，但在判定完成前不计入 `er`；责任投手统计列不存在时自动补建（teamId 取该半局守备方：上半局主队、下半局客队），随后照常应用差额。

当前 LiveGame 已传送跑者责任投手及逐事件壘況信息，但仍未将所有事件完整持久化并按“无失误局面”重播；复杂的野手选择、触杀/封杀、妨碍、申诉、多跑者推进等案例仍需要更完整事件模型与端到端验证。捕逸影响字段已加入 API 与持久化契约，LiveGame 尚未提供官方记录员输入控件；没有明确值时会保留 `PENDING`，可经人工覆核解决。

### 棒球统计指标数据结构与计算逻辑
- 击球（Batting）
  - 基础字段：GP、PA、AB、R、H、RBI、HR、InsideParkHR、SB、BB/HBP、SO、Doubles、Triples、E、GDP、SH、SF、BB、IBB、HBP、IO、CS
  - 衍生字段：Singles、TB、AVG、OBP、SLG、OPS、SB%
  - 计算要点
    - PA = AB + BB + HBP + SF + SH + IO（BB 含 IBB；IO 为妨阻上垒）
    - 一安打数 = H - (二垒打 + 三垒打 + 全垒打 + 场内全垒打)
    - 总垒打数 = 一×1 + 二×2 + 三×3 + 全×4 + 场内全×4
    - AVG = H / AB（AB>0时）
    - OBP = (H + BB + HBP) / (AB + BB + HBP + SF)；旧数据只有 BBHP 合计时用合计回退
    - SLG = TB / AB（AB>0时）
    - OPS = OBP + SLG（AB>0且OBP分母>0时）
    - SB% = SB / (SB + CS)（有尝试时）
- 投球（Pitching）
  - 基础字段：GP、IP、ER、PitchH、PitchDoubles、PitchTriples、PitchSh、PitchSf、PitchBbHp、PitchSo、PitchHr、PitchInsideParkHr、PitchIo、GS、SVO、CG、PG、W、L、SV、HLD、PitchPa、PitchBf、PitchAb、NP、PitchBb、PitchIbb、PitchHbp、WP、BK、PitchR、GO、FO
  - 衍生字段：WHIP、ERA、GO/FO
  - 口径：PitchBb 含 IBB；PitchBbHp = PitchBb + PitchHbp；PitchDoubles/Triples/Sh/Sf/Io 为“被”统计，不参与 ERA/WHIP
  - 计算要点
    - WHIP = (H + BB) / IP（IP>0时，HBP 不计入标准 WHIP；旧数据只有 BBHP 合计时用合计减 HBP 回退）
    - ERA = 9 × ER / IP（IP>0时）
    - GO/FO = GO / FO（FO>0时）
- 防守（Fielding）
  - 基础字段：GP、INN、TC、PO、A、E、DP、PB、CatcherCs、CatcherSb
  - 衍生字段：TC%
  - 计算要点
    - TC优先取直接值，否则用 PO + A + E
    - TC% = (PO + A) / TC（TC>0时）
    - INN 统一为标准棒球局数格式

## 依赖关系分析
- API → Service：接口层仅做参数校验与转发，不承载业务逻辑

## 性能考虑
- 查询与聚合
  - 将聚合计算尽量下推到数据库层（通过Mapper SQL），避免在应用层进行大规模计算
  - 使用分页与限制返回条数（如游戏日志limit上限），防止大结果集导致内存抖动
- 去重与择优
  - 对同角色多记录采用“丰富度评分”择优，减少冗余传输与展示
- 缓存策略建议
