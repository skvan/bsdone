## Purpose and six elements

This draft inventories user-visible LiveGame operations found in the current source and the P1/P2/P3 log work. It maps current generator behavior tests separately from browser interaction evidence. It does not independently define baseball rules or game-format policy.

Each applicable log should make these six elements explicit or unambiguously recoverable:

| Key | Element | Coverage question |
| --- | --- | --- |
| S | Subject | Who performed the action or is affected? |
| A | Action/result | What happened, including safe/out/result? |
| K | Key detail | What detail distinguishes this play (pitch, base, position, out type, RBI, etc.)? |
| C | Consequence | What changed in bases, outs, score, inning, or batting order? |
| R | Reason/causal chain | Why did the result occur, and how are linked actions represented? |
| T | Totals | Which relevant cumulative/statistical result is recorded or explicitly not applicable? |

For any element that truly does not apply, the eventual approved matrix must say `N/A` with a reason. A blank cell is not evidence of coverage.

### Historical backup sample audit

The checked-in `bsball_backup.sql` was inspected read-only; no database restore or mutation was performed. It contains 152 game rows, 27 parseable non-empty live snapshots, 398 at-bat summaries, and 230 summaries with `basesBefore`, `outsBefore`, and `batterOrder`. The matching snapshots contain no persisted `playEvents` arrays. A conservative match on inning, half, batting-order number, and batter name linked 193 of the 230 rich summaries to a visible batter-result log line; 90 linked plays started with at least one occupied base, and 57 started with two outs. Eight summaries in one snapshot all linked to the visible log sequence, but they are not a representative ten-play sample (they have no occupied bases or scoring plays).

This proves there is useful existing data for selecting and cross-checking historical plays; it is not correct to say that no historical IDs/data exist. It does **not** yet pass the acceptance that a reader can reconstruct bases, outs, score, and batting order from the log tab alone: the backup's at-bat summaries carry pre-play bases and outs that the matching batter-result line does not consistently repeat. Across those 193 linked plays, nearby log lines contained scoring language for 28 cases, but the score is not consistently stated as a numeric before/after total. Therefore the snapshot can act as an oracle for an audit, but cannot be used to fill information absent from the log itself. A full ten-play audit must record both the log-only reconstruction and the snapshot oracle side by side, including explicit `ambiguous/missing` outcomes rather than silently borrowing snapshot fields.

### Browser E2E gap and practical route

The checked-in `e2e/live-game-save.spec.js` proves login, a save request, and that a snapshot exists. It does not click a scoring/play action, assert the generated log, verify stats, undo/re-record, reload, or compare the viewer. The local run also requires `E2E_TENANT`, `E2E_USERNAME`, `E2E_PASSWORD`, `E2E_EVENT_ID`, and `E2E_GAME_ID`; none are configured in this environment. Do not put credentials in the repository or an issue comment.

To make this runnable without using a real match, the preferred implementation is an isolated QA game/tenant plus test-only credentials stored as GitHub Actions secrets, with the browser test creating or resetting a disposable game fixture. The E2E should perform one action through LiveGame, wait for the save request, assert the posted event/log/stat payload, reload and assert persisted values, then open the viewer and compare its log/dynamics; a second deterministic case should record, undo, repeat, and compare the exact text. Until that fixture and credentials exist, run generator/state integration tests locally and mark the hosted E2E as blocked/skipped, never passed. A mocked-browser flow can validate UI wiring but must be labeled separately because it cannot prove backend persistence.

## Coverage calculation (strict row-level rule)

For the approved matrix, calculate coverage as:

`passed rows / total approved rows * 100%`

A row counts as passed only when it has a named, rerunnable test that asserts the row's required behavior and all applicable S/A/K/C/R/T elements, and that test passes. Missing tests, skipped tests, historical results without checked-in test source, partial helper coverage, and unconfirmed expected behavior all count as **not passed**. The total row count must come from the approved frozen Appendix A; do not substitute a reconstructed candidate list.

| Matrix scope | Total rows | Fully tested and passing | Missing/partial/skipped/unconfirmed | Strict coverage |
| --- | ---: | ---: | ---: | ---: |
| Current reconstructed candidate matrix (not authoritative) | 21 | 0 | 21 | 0/21 = 0% |
| Frozen v1.0 Appendix A (strict evidence verified in this checkout) | 35 | 0 | 35 missing/unmapped/unconfirmed | **0/35 = 0% verified** |

The 0/35 figure is an evidence-completeness result under the requested strict rule, **not** a claim that all 35 behaviors are broken. A row can only pass once its official definition, expected six-element content, named rerunnable test, and passing result are mapped. The exact official row definitions are missing from this checkout; existing helper tests (including the 26 focused log-text tests) do not yet prove any official row end to end. Missing, skipped, or unconfirmed rows are not counted as passing.
